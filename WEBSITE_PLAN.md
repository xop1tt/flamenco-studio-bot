# Flamenco Studio Website
## План разработки веб-сайта

> **Статус (октябрь 2026).** Документ — исходный план и требования; текущее
> устройство описано в `README.md` этого репозитория и README сайта.
> Реализованы этапы 0–7: общие сервисы, веб-API, публичный сайт, вход через
> Telegram, личный кабинет, запись и **отмена записи** (правило бота: не
> позднее чем за 24 часа, пауза 12 часов на повторную запись), оплата
> (сайт готов, ЮKassa для сайта включается `WEB_YOOKASSA_RETURN_URL`).
> Время везде показывается в часовом поясе студии `STUDIO_TIMEZONE`
> (по умолчанию `Europe/Moscow`). Админ-панели на сайте нет (этап 8) —
> администрирование остаётся в Telegram-боте. Продуктовый roadmap (октябрь
> 2026) добавил в backend: отмену занятия студией с возвратом занятий и
> перенос, абонементы с остатками, историю, уведомления (outbox), вход и
> привязку Telegram через бота и API кабинета — см. `docs/api.md`.

## 1. Цель проекта

Добавить полноценный веб-сайт для Flamenco Studio к существующему Telegram-боту.

Веб-сайт должен использовать существующую бизнес-логику, PostgreSQL и данные проекта, а не создавать параллельную систему.

Главный принцип архитектуры:

```text
                    ┌─────────────────┐
                    │   Telegram Bot  │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │ Shared Services │
                    │                 │
                    │ Users           │
                    │ Schedule        │
                    │ Booking         │
                    │ Payments        │
                    │ Support         │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │   PostgreSQL    │
                    └─────────────────┘
                             ▲
                             │
                    ┌────────┴────────┐
                    │    Web API      │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │  Web Frontend   │
                    └─────────────────┘
```

Telegram и сайт должны работать с одной системой данных и одинаковыми бизнес-правилами.

# 3. Главный архитектурный принцип

Нельзя создавать две независимые реализации одной бизнес-логики.

Плохая архитектура:

```text
Telegram
    ↓
Telegram business logic


Website
    ↓
Website business logic
```

Правильная архитектура:

```text
Telegram Handler ──────┐
                       ▼
                 Shared Service
                       ▲
                       │
Web API ───────────────┘
```

Например:

```text
Telegram → BookingService
Web API  → BookingService
```

Аналогично:

```text
UserService
ScheduleService
BookingService
PaymentService
SupportService
```

Если текущая реализация содержит бизнес-логику непосредственно внутри Telegram handlers, её следует постепенно вынести в переиспользуемые сервисы.

При этом существующий Telegram-бот не должен перестать работать.

# 9. Авторизация

Предпочтительный способ авторизации:

## Telegram

Пользователь должен иметь возможность связать веб-сайт с существующим Telegram-пользователем.

Не создавать отдельную независимую учётную запись без необходимости.


Перед реализацией необходимо изучить существующую систему идентификации пользователей и выбрать безопасный способ интеграции.

Не хранить Telegram bot token или другие секреты во frontend.

# 13. Бронирование

Пользователь должен иметь возможность записаться на свободное занятие.

Критически важно сохранить существующие правила бронирования.

Особое внимание:

- проверке вместимости;
- конкурентным запросам;
- предотвращению двойной записи;
- транзакционности;
- корректному изменению состояния;
- обработке ситуации, когда последнее место одновременно пытаются занять несколько пользователей.

Нельзя полагаться только на frontend-проверку:

```text
Frontend:
"есть место"

Backend:
"записываем"
```

Проверка должна выполняться безопасно на backend/database уровне.

Если текущая система уже решает эту проблему транзакциями, использовать существующий механизм.

# 16. Платежи

В существующем проекте может использоваться YooKassa.

Перед интеграцией сайта необходимо изучить существующую реализацию платежей.

Главный принцип:

```text
Website
   ↓
Payment Service
   ↓
YooKassa
   ↓
Payment verification
   ↓
Balance / ledger
```

Не создавать отдельную веб-систему платежей.

Особенно сохранить:

- идемпотентность;
- проверку статуса платежа;
- корректное начисление;
- защиту от повторного начисления;
- ledger, если он уже используется;
- возвраты, если они уже реализованы.

Никогда не доверять frontend сообщению:

```text
"Оплата успешна"
```

Факт успешной оплаты должен подтверждаться backend через надёжный механизм.

# 30. Правило разработки

Работать по одному этапу.

После завершения каждого этапа:

1. Запустить тесты.
2. Проверить существующий Telegram-бот.
3. Проверить новые функции.
4. Проверить git diff.
5. Проверить отсутствие секретов.
6. Объяснить изменения.
7. Только после подтверждения переходить дальше.

Не реализовывать весь сайт одним огромным изменением.

---

# 31. Definition of Done

Этап считается завершённым только если:

- код работает;
- существующий функционал не сломан;
- тесты проходят;
- нет очевидных security issues;
- нет секретов в git;
- database migrations корректны;
- API валидирует данные;
- frontend корректно обрабатывает ошибки;
- изменения понятны и документированы.

---

# 32. Главный принцип проекта

Не переписывать работающую систему только потому, что создаётся сайт.

Сначала использовать существующую архитектуру и данные.

Рефакторить только там, где это необходимо для:

- переиспользования бизнес-логики;
- безопасности;
- тестируемости;
- API;
- поддержки веб-клиента.

Цель:

```text
Один backend
Одна БД
Одна бизнес-логика
Два интерфейса

Telegram + Website
```
